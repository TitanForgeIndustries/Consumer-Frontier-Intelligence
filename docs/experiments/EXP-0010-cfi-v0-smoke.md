# EXP-0010: Independent CFI v0 sparse-capacity smoke

Predeclared 2026-09-23, before the run; completed 2026-09-23. This is a new experiment, not a continuation of Q/R. The CFI-defined model and its dense control train from scratch. No Qwen weights or tokenizer are loaded.

## Hypothesis and limits

Can a shared causal core with hierarchical top-1 expert dispatch execute one expert per token while training, saving, loading, and generating in isolation? The smoke tests engineering viability and records a first paired control. It cannot establish higher quality, efficient paging, general intelligence, or meaningful real-world speedup. The selected experts are computed sparsely but **all weights stay in GPU memory**.

## Predeclared procedure

- Corpus: public `karpathy/char-rnn` tiny Shakespeare `data/tinyshakespeare/input.txt`, pinned to a source commit at download. Record URL and SHA-256 in the completed record. This deliberately tiny language distribution is only an engineering smoke corpus.
- Byte vocabulary 256; contiguous 90%/10% train/validation split, no tokenizer pretraining.
- Seed 42; 32 optimizer steps per mode; AdamW 3e-4, weight decay 0.01; batch 8, window 128 bytes; auxiliary load-balance loss coefficient 0.01 for sparse only. Identical sampled train and validation windows per mode.
- Width 256, four causal blocks, four heads, shared FFN width 512; four groups × two experts, expert width 512; context 256. Dense control executes one width-512 FFN instead of experts/router.
- Held-out NLL: four batches of eight 128-byte windows, same seed/windows in both modes. Greedy generation uses prompt `The ` and 64 new bytes per mode. Fixed-token timing: 4-byte warmup followed by 16 generated bytes, two repeats. Record total/resident and estimated active parameters, expert load/switch rate, seconds/tokens per second, peak allocated CUDA bytes, exact bytes/text, raw corpus and checkpoint hashes.
- Run in a fresh Python process with the required dependencies installed. Write artifacts to a new directory under the local data root, outside tracked Git files; never include corpus or checkpoints in Git. Stop on nonfinite loss or a new implementation failure. A CUDA assert requires another process.

## Implementation failure, separate from scientific results

The **first post-training standalone dense CLI invocation failed**, after the completed training run, with `UnicodeEncodeError` at `scripts/generate_cfi_v0.py:28`: the decoded U+FFFD replacement characters could not be encoded by a Windows `cp1252` stdout stream. This did not change model weights, validation, timing, or the saved generation bytes. The separate raw record is `implementation_failure-standalone-inference.json` in the historical result directory. Reconfiguring CLI stdout as UTF-8 fixed display; a regression test using a strict cp1252 stream passed, then independent CPU CLI processes for **both** original checkpoints exited successfully and reproduced the raw bytes. No training rerun was used to erase this failure.

## Interpretation and decision

**Engineering smoke passed:** an original CFI-defined causal model trained, saved, reloaded, and generated without Qwen weights; the physically selected expert path and paired dense control are exercised. This is only a 4.35M-parameter smoke, not the proposed 100M–500M candidate or a useful language model. It is not frontier intelligence.

**Sparse-capacity advantage not established:** sparse held-out NLL was worse by 0.5853724479675293, throughput was 0.3976644376365809× dense (about 2.51× slower in this fixed-token setup), and peak CUDA allocation was higher (42.63 versus 35.58 MiB). Every held-out token selected expert 7; the load-balancing coefficient did not prevent route collapse. The 1.0 adjacency statistic here is trivial collapse, **not** evidence of useful predictable expert locality. Estimated inactive expert parameters (42.34% of the sparse model) are not a wall-clock or resident-VRAM saving. Generation recomputes the entire cropped context with no KV cache; GPU weights for all experts remain resident. Timing comprises two short repeats, not a stable throughput study.

Close EXP-0010 as a successful *runnable-infrastructure* smoke and a negative preliminary quality/performance result under this tiny budget. Do not scale or claim sparse benefit from it. A separately predeclared follow-up would need longer training, multiple seeds, router-collapse controls, parameter-matched dense comparison, real profiling, and meaningful held-out evaluation. None was started here.
